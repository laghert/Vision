# Deduplikacja profili podczas pierwszej synchronizacji Librus

Zmiana ponownie używa istniejącego profilu Librus po `accountId`/`accountLogin`, zachowuje jego ID i odświeża dotychczasowy `LoginStore`. Po synchronizacji nadal puste duplikaty trafiają do opcjonalnego usuwania, którego cleanup obejmuje teraz notatki i ręczny plan. Obecne granice dopasowania oraz obsługa `NotFound` tworzą jednak ścieżki utraty danych. Zgłoszony `assembleDebug` przeszedł; nie obejmuje opisanych scenariuszy runtime.

**Watch for:** **[P1 · confirmed]** zaakceptowany `NotFound` może wyczyścić dane po dowolnym GET; **[P1 · confirmed]** archiwum może zostać wybrane i nadpisane jako profil kanoniczny; **[P2 · confirmed]** częściowo nowy portal wielouczniowski rozdziela uczniów na różne `LoginStore`; **[P2 · likely]** korutyny mogą wrócić do zniszczonego widoku; **[P3 · confirmed]** anulowanie pierwszego dialogu pomija pozostałe puste duplikaty.

**Verdict**: NEEDS_CHANGES

## High-level view

**[P1 · confirmed]** `ERROR_LIBRUS_API_DATA_NOT_FOUND` jest ignorowany dla wszystkich GET-ów z profilem, nie tylko opcjonalnych endpointów. Błędna odpowiedź trafia do zwykłego parsera, więc sync może zakończyć się sukcesem z pustymi kolekcjami potraktowanymi jako aktualny stan źródłowy.

**[P1 · confirmed]** deduplikacja wybiera niepusty profil o najniższym ID również spośród archiwów. Ponowne logowanie może przez to zsynchronizować i nadpisać historyczny profil zamiast aktywnego.

**[P2 · confirmed]** gdy portal wielouczniowski zwraca istniejącego i nowego ucznia, dopasowany profil zachowuje stary store, a nowy pozostaje przy store bieżącej sesji. Jedno konto portalowe przestaje więc współdzielić stan logowania.

**[P2 · likely]** praca IO używa `Job` instancji fragmentu, który nie jest anulowany wraz z widokiem. Po rotacji lub nawigacji wynik może użyć nieaktualnego `activity`/`nav`, a pamięciowa kolejka cleanupu nie przeżywa odtworzenia aktywności.

**[P3 · confirmed]** kolejka usuwa ID przed dialogiem i przechodzi dalej tylko po usunięciu. Przy dwóch pustych duplikatach „Anuluj” na pierwszym powoduje, że drugi nie zostanie zaproponowany.

## `NotFound` przechodzi jako sukces i może skasować dane lokalne

**[P1 · confirmed]** `LibrusApi.apiGet` dopuszcza każdy `ERROR_LIBRUS_API_DATA_NOT_FOUND`, jeżeli metoda to GET i `data.profile != null` (`LibrusApi.kt:74-87`). Warunek obejmuje także wymagane endpointy, m.in. `Me` i `Classes`, po czym wywołuje `onSuccess(json)` z odpowiedzią błędną (`LibrusApi.kt:96-97`). `LibrusApiMe` zapisze wtedy puste dane użytkownika, a `LibrusApiClasses` uzna endpoint za zsynchronizowany mimo braku klasy.

Końcowy `Data.saveData` bezwarunkowo czyści część map (`Data.kt:237-242`) i zapisuje puste listy z `removeNotKept = true` (`Data.kt:286-293`). `NotFound` dla ocen, obecności, planu lub zadań może więc zakończyć sync jako poprawny, oznaczyć profil jako niepusty i usunąć wcześniej zapisane rekordy.

Poprawka powinna przywrócić domyślne fail-closed i dopuszczać `DATA_NOT_FOUND` jawnie per endpoint przez `ignoreErrors` albo parametr „optional empty”. Ta ścieżka nie może przekazywać błędnego JSON-u do zwykłego parsera; musi też jawnie zdecydować, czy brak zbioru oznacza jego wyczyszczenie, czy zachowanie starego stanu.

## Profil archiwalny może zostać kanonicznym celem synchronizacji

**[P1 · confirmed]** kandydaci pochodzą z `profileDao().allNow` i są filtrowani tylko po `loginStoreType`, bez odrzucenia `archived` (`LoginProgressFragment.kt:161-180`). Niepuste archiwum ma pierwszeństwo przed pustym aktywnym duplikatem, a wśród niepustych wygrywa najniższe ID. Wybrany obiekt jest następnie zapisany przez `REPLACE` i jawnie przekazany do synchronizacji (`LoginSyncFragment.kt:87-96`), chociaż standardowa lista synchronizacji wyklucza `archived = 1`.

Bieżące dane mogą nadpisać archiwalny rok, podczas gdy profil pozostanie oznaczony jako archiwalny. Kandydatów trzeba ograniczyć co najmniej do `!archived`; wiele aktywnych rekordów należy rozstrzygać bez dotykania archiwów.

## Częściowo nowy portal rozszczepia wspólne poświadczenia

**[P2 · confirmed]** dopasowany uczeń dostaje `canonicalProfile.loginStoreId`, natomiast niedopasowany zachowuje `event.loginStore.id` nadany w `LibrusFirstLogin` (`LoginProgressFragment.kt:182-205`). Dla portalu zwracającego istniejącego ucznia A i nowego B wynik zawiera dwa `LoginStore`, mimo jednego logowania portalowego.

Odświeżenie tokenu podczas późniejszej synchronizacji zapisze tylko store danego ucznia, więc stan sesji rodzeństwa zacznie się rozchodzić. Dla całej odpowiedzi `LIBRUS_EMAIL` trzeba wybrać jeden kanoniczny store i przypisać do niego wszystkie profile; historyczne store wolno usunąć dopiero po sprawdzeniu pozostałych referencji.

## Wynik uzgadniania może wrócić do nieaktualnego fragmentu

**[P2 · likely]** nowe `launch { withContext(IO) ... }` korzystają z własnego `Job`, ale fragmenty nie anulują go w `onDestroyView` ani `onDestroy` (`LoginProgressFragment.kt:125-149`, `LoginFinishFragment.kt:88-106`). Po rotacji, cofnięciu lub zamknięciu aktywności wynik nadal odwołuje się do starego `activity`, `nav` albo dialogu. Progress fragment usuwa sticky event przed IO, więc odtworzona instancja nie odzyska też tego wyniku.

Możliwa jest nawigacja z nieaktualnego destination, pokazanie dialogu po zapisaniu stanu albo ponowne uruchomienie first login. Należy użyć `viewLifecycleOwner.lifecycleScope`, trzymać wynik i kolejkę w `ViewModel`/`SavedStateHandle` oraz sprawdzić lifecycle/destination przed UI.

## Anulowanie pierwszego cleanupu porzuca drugi pusty duplikat

**[P3 · confirmed]** `offerEmptyDuplicateRemoval` zdejmuje pierwszy ID przed pokazaniem dialogu (`LoginFinishFragment.kt:88-105`). Następny element jest obsługiwany tylko wtedy, gdy profil nie istnieje/nie jest pusty albo po pozytywnym usunięciu; neutralne „Anuluj” wyłącznie zamyka dialog. Dla dwóch pustych duplikatów drugi nie zostanie zaproponowany.

ID powinno być zdejmowane po rozstrzygnięciu, a callback końcowy kontynuować po usunięciu i po świadomym pominięciu. Jeżeli anulowanie ma przerwać całą serię, UI musi komunikować tę odmienną akcję jednoznacznie.
